Auto-Parallelism

When you build a program natively, J2 parallelizes idiomatic loops across your CPU cores — automatically, with no annotations and no change to your code.

How it works

The interpreter (the default j2 FILE) runs single-threaded. When you compile with j2 build (or set J_FORCE_NATIVE=1), J2 lowers your program to native code and recognizes common loop shapes. A loop that matches a known parallelizable pattern is rewritten to run in parallel across cores; everything else runs as ordinary serial native code.

You don't mark anything as parallel. You write the obvious loop, and the compiler decides whether it can be split safely.

What gets parallelized

The compiler recognizes the patterns that show up in numeric and data code, including:

  • Reductions — summing or combining a sequence into one value.
  • Element-wise maps — writing dst[i] from src[i] (scaling, adding two sequences, applying a function over a sequence).
  • AXPY / fused multiply-add — y[i] = y[i] + a * x[i].
  • Matrix×vector and 1-D convolution — nested loops over a[i*n + j].
  • Independent calls — two independent, pure function calls can run concurrently.
# A reduction and an element-wise map — both parallelize under `j2 build`.
func dot(a, b) = {
    s := 0.0
    for i in 0..(len(a) - 1) { s = s + a[i] * b[i] }
    give s
}

Correctness first

Parallelization never changes results. Every native build — parallel or not — is checked against the same program run through the interpreter and the plain serial path; they must produce byte-identical output. If a pattern can't be proven safe to split, the loop simply runs serially. The headline feature is opt-out-by-being-wrong: it only fires where it's provably equivalent.

Task parallelism: independent calls

When a function makes several independent calls and then combines their results, J2 runs those calls on separate cores — no threads, no annotations, just ordinary function calls:

func estimate(n: int) -> float = {
    a := count_hits(1, n)          # these four calls are
    b := count_hits(999983, n)     # independent, so they run
    c := count_hits(50000017, n)   # concurrently across cores
    e := count_hits(1234567891, n)
    total := a + b + c + e
    give (total * 4.0) / (4.0 * (n * 1.0))
}

This is where parallelism pays off most: each call does real compute-bound work (here, a Monte-Carlo dart throw loop), so the speedup scales with the number of independent calls rather than being capped by memory bandwidth. The examples parallel_montecarlo.j2 and parallel_integrate.j2 in j-examples/ use exactly this pattern.

Using it

# Compile once, run fast repeatedly:
$ j2 build sim.j2 -o sim
$ ./sim

# Or force the native+parallel path for a single run:
$ J_FORCE_NATIVE=1 j sim.j2

# Reproduce the example speedups (parallel vs single-threaded):
$ j-examples/bench_parallel.sh

What to expect

Parallelism helps most when the work is compute-bound — lots of arithmetic relative to memory traffic. Measured on an 18-core machine (parallel vs the same native build with parallelism off):

ExampleKindSpeedup
parallel_integratetask-parallel, compute-bound~2.9×
parallel_montecarlotask-parallel, compute-bound~2.5×
parallel_matvecdata-parallel, memory-bound~2.2×

For memory-bound kernels — those that mostly stream large arrays with little arithmetic, such as a single pass of matrix×vector — speedup is limited by memory bandwidth rather than core count, so the gain plateaus (around 2× here) no matter how many cores you add. That's a property of the workload, not of J2: the compute-bound task examples above keep scaling where the bandwidth-bound one cannot.

Set J_NO_NESTED=1 to disable the nested-loop matchers (matrix×vector and friends) while keeping the single-loop families — a kill-switch for bisecting or maximum conservatism. J_PARALLEL=0 disables auto-parallelism entirely (native, single-threaded).
